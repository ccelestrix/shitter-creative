# Creative on 12.41 (Chapter 2 Season 2)

12.41 runs Unreal Engine 4.24. Upstream Reboot only showed the **Creative** tick box for engine 4.22-4.23, so on 12.41 Creative could not be switched on at all.

## Changed so far
- The Creative tick box now shows for engine 4.22 to 4.24.
- `ShowPlayset` logs an error and returns instead of crashing when the playset loader address was not found for the version.
- `AFortAthenaCreativePortal::GetCreatorName` no longer dereferences a null pointer.
- A missing `CreativePortalManager` on the game state is logged (`LogCreative`) instead of crashing.

## Not tested yet
None of this has been run against a 12.41 client. To find what breaks next, start a 12.41 server with Creative ticked and read the `LogCreative` lines.

## Likely next problems (from reading the code)
- `Addresses::LoadPlayset` is found by a string search. If it comes back 0 on 12.41, islands will not load their playset.
- The code assumes the 4.23 field names on the portal (`LinkedVolume`, `bPortalOpen`, `OwningPlayer`) and on the controller (`OwnedPortal`, `CreativePlotLinkedVolume`). A rename in 12.41 shows up as an offset error in the log.
- Saving and loading island contents is not implemented.

## Logs
- `xenbono.log`: every line from every logger, written straight to disk in the game's working directory (falls back to the exe folder, the DLL folder, then temp if that folder is not writable). The first line says which folder was used.
- `xenbono_creative.log`: only the Creative lines (`LogCreative`), written next to the game executable. It starts with a report of which Creative functions and addresses were found, then logs island setup, the hub teleport, portal teleports and creative item requests.

## Island creation (ported from the Xenon server, checked against the 12.41 SDK)
- A new island starts as the `Temperate_Medium` plot (the first one on the Select Type screen) and its playset.
- The level save component is told the plot is the player's, loaded from the plot, and public. Without that the client says creating and saving islands does not work.
- The portal, island volume and controller now call their `OnRep_` functions so clients see the change (the loading screen and the island appearing come from these).
- Entering the island gives the creative phone, links the volume to the player and drops them in from the sky (Z 10000, then `BeginSkydiving`).
- Every creative `Server*` call the client makes (claim/release portal, load/save checkpoint, load plot, set playset, ...) is logged to `xenbono_creative.log`. Picking a layout (`ServerSetPlayset`) loads that playset into the island.
- Still missing: saving and loading real island contents.

## What is missing from the executable (and what XENBONO does about it)
The Fortnite executable has no dedicated-server code, so some of Creative's server side is simply not there (found by testing, confirmed by people who have done Creative before). XENBONO reimplements the parts it needs. Everything it does is logged to `xenbono_creative.log`.

- **Start Game / End Game** (`CreativeMinigame` in `FortAthenaCreativePortal.cpp`): after Start the game moves the island's minigame to Transitioning and stops. A small driver (tick box "Drive Start Game / End Game") moves it on, following what the Xenon server does in `FortMinigame.cpp`: teams (3 and up) and `OnPlayerPawnPossessedDuringTransition` for each player, `AdvanceState` then `HandleMinigameStarted`, `OnClientFinishTeleportingForMinigame` and a second's wait in WaitingForCameras, then Warmup, InProgress, the time limit, End Game and the reset back to editing. Each step calls the game's own function first (`AdvanceState`, `EndGame`, ...), checks the result, and sets the state itself only if nothing happened.
- **Prefabs / galleries / devices** (devices are thrown as `CP_PlaysetGrenade_...` items, so they are prefabs too): the grenade explodes and spawns a prefab volume with the playset set, but the volume never initialises (no stream component, state 0) and the game's record-spawn step finishes with nothing. A prefab is not a streamed level: it is a list of props, each a saved record (`PlaysetPropLevelSaveRecordCollection`: soft record, name, transform). What a thrown prefab does, in order (tick boxes in the Game tab, "Activate thrown prefab volumes" is on by default):
  1. `SpawnActorsInPlayset` (with an actor probe, the spawn may be asynchronous);
  2. a check of the volume manager (is it "loading islands", is the volume registered; it lowers a stuck loading counter and registers the volume);
  3. a read-only description of the prefab's data and raw bytes of the first records, so the layout of the opaque record structs can be worked out from the log;
  4. tick box "apply the props' saved records": the volume manager's own `ApplyLevelSaveToWorld` for the first 3 records, with probes that log where new actors appear;
  5. `SetCurrentPlayset`, streaming only if a stream component appears;
  6. tick box "also mark their volume Ready" (tested on its own, an earlier version of it was followed by a crash);
  7. the volume manager's queue (`TryActivateQueuedVolumes`).
  Actor probes write `Actor probe '...' after N ms: M new actors: ...` with the class and position of the new actors.
- **Memory bar**: logged (`Budget (...)`), the cost directory is reported and loaded; costs are not computed yet.
- **Islands / settings / devices**: partly present; see the log lines for what each call did.

## If the server never becomes joinable (stuck on the loading screen)
- The server only starts listening once the creative hub's `FortPlayerStartCreative` actors exist. They come from the hub level (`CreativeHub_S11_01_Creative_Spawns`), one of the playlist's three levels. The playlist levels are not streamed by the game state: `StreamLevel` spawns a `BuildingFoundation3x3` actor for each level and that actor streams it, so a lost request is never repeated by the game.
- While the player starts are missing, `xenbono_creative.log` says every 4 seconds (every 20 s after the first 80 s): which world this is, how many player starts exist, which of the playlist's levels have a streaming level (`MISSING` if not), what each streaming level is doing (loaded, visible, pending, should-be-loaded) and what each streaming foundation holds.
- After 8 s a creative streaming level that exists but is not loaded is told to load and become visible. After 10 s, and again after 30 s, a playlist level that still has no streaming level at all is requested again (only that level, so nothing is loaded twice). Each of these is logged as a warning.
- If it still never listens, the useful extra file is the engine log of the server process (`FortniteGame\Saved\Logs\FortniteGame.log` next to the exe), which holds the real load error.

## What the client's files really hold (the creative data inspector)
- Result of the 5 Nov test (barn prefab, explosive barrel and creature placer devices): every thrown playset reports `streams level not set, level save record null, cooked 0`. The barn lists 39 associated props, the devices list none and are 1 x 1 x 1. `SpawnActorsInPlayset` adds no actors. So the files of this client do not give the server anything to spawn from; the game's own prefab code has nothing to work on, or is not there (or both).
- The SDK dump (`SDK.rar` from OGS-12.41, made with Dumper-7) is the real 12.41 layout of every playset, prop, volume, volume manager and record class. It shows `ActorTemplateRecord` (0x58 bytes) and `ActorInstanceRecord` (0x70 bytes) as blank padding because those structs are written and read by native code, not through reflection. No other public source describes them (Epic only documents the idea: template records hold an actor class and its property settings, instance records hold a placement and point at a template). Their layout has to be read from the running game.
- What the DLL now writes to `xenbono_creative.log` so that no layout is guessed:
  - `Pak files:` the pak files next to the exe (whether any server or creative chunk exists), at startup and in the survey.
  - `Asset registry ...:` what the cooked asset registry lists under `/Game/Playsets` and `/Game/Creative`, and the assets of the playset, prop, grenade and record classes, loaded or not.
  - `Survey ...:` every playset, prop and record the game has loaded, with which of them carry a level, a spawn item, a record or props, plus the level save components of the islands. Written by the button "Write what the creative data holds to the log" (in a creative game) and once automatically at the first thrown prefab.
  - `Playset dump <name>`, `Prop dump <name> #n`: every property of a thrown playset and of its first three props with type, offset and value (arrays, maps and structs included; a struct with no reflected members is shown as raw bytes). A prop's actor record is dumped and described the same way when it exists.

## Our own prefabs
- The files have no data for the real prefabs, so a thrown prefab that has props (or a footprint bigger than 1 x 1) is built from ordinary wood building pieces: walls on the four edges of its footprint (2 high, a door gap on the south side) and a flat roof of floor pieces. Footprint = the playset's SizeX x SizeY, capped at 10 x 10, centred on the volume the grenade made. Written in `BuildOwnPrefab` (FortAthenaCreativePortal.cpp); tick box "Thrown prefabs: build our own version from building pieces".
- Devices (1 x 1 x 1, no props) are not built this way; they need their real actor classes.
- Geometry assumption to check in the game: pieces are placed by a corner (walls run from the corner along their +Y), tile 512 wide, wall 384 high, taken from the pieces players placed in the logs. If the walls come out shifted or rotated, that is the place to adjust.

## Our own devices
- The asset registry (listed through reflection, no loading) shows what the build holds: 724 playsets, 16,879 props and 629 playset grenades under `/Game/Playsets`, and under `/Game/Creative` 531 maps, 2,009 blueprints and one map per device (`/Game/Creative/Maps/Devices/CP_Devices_<Name>`, about 50 devices) with the device's blueprints in `/Game/Creative/Devices/<Name>`. There are no maps for the prop-based prefabs, no `LevelSaveRecord` asset anywhere.
- A thrown `PID_CP_Devices_<Name>` is therefore built by `BuildOwnDevice`: the registry lists `/Game/Creative/Devices/<Name>`, the blueprints are tried best name first (`BP_<Name>`, `<Name>_GBA`), the first one that is a building actor is spawned in the volume the grenade made, with the thrower's team and the build animation. `Own device <Name>:` lines in `xenbono_creative.log` say what was found and tried.

## Prefabs from the real pieces
- Every playset carries `ActorClassCount`: the classes it is made of and how many of each (the IceCastle walls, the farm roofs, the bank's balconies ...). It says what and how many, not where. `BuildPrefabFromClasses` builds a prefab out of those real pieces instead of player pieces: floors on the ground, walls round the edge of the footprint (door front centre, windows and arches spread out in proportion), a roof, stairs inside and the remaining pieces as decoration. The footprint is the playset's SizeX x SizeY (max 12), the number of wall levels follows from how many wall pieces there are (1 to 3).
- Placement is a guess (pieces are assumed to sit by a corner on a 512 grid with 384 high walls, like the player pieces); the log line `Own prefab (real pieces): built N pieces ...` and the `piece <class> xN as <kind>` lines say what was used. A playset that lists no loadable pieces falls back to the wood house.
- Layout v2: every piece class is measured first (spawned once high above the prefab, its bounding box read with `GetActorBounds`, then removed) and placed by the middle of its box, so the unknown pivots no longer matter. The wall panel with most pieces sets the pitch along the edge and the height of a level; panels are turned so their long side runs along the edge; pillars (and columns) go to the corners and edge middles instead of taking wall slots; caps, battlements and rails run along the top edge; floors and roofs are gridded by their own size; decoration is laid out in rows inside, spaced by its own size; wall lights and wall art are left out. The log lists each class with its measured box.

## Devices from their map (replaces the folder search)
- The 5 Nov test showed the folder search does not work for most devices (`/Game/Creative/Devices/Speaker` holds nothing). Every device does have a map `CP_Devices_<Name>` under `/Game/Creative/Maps/Devices` (found through the asset registry). `ReadDeviceMap` loads that map as an asset only (it is not streamed in), reads `PersistentLevel.Actors` (ULevel::Actors is at 0x98 in this build) and for each actor of one of the game's own blueprints takes its class, relative location, rotation and scale from its root component. `BuildOwnDevice` spawns the same actors in the volume the grenade made, lifted by the playset's own location offset (75 for devices), and tells building actors who built them.
- `Device map <Name>:` and `map actor N:` lines say what was found; the folder search stays as the fallback when no map is listed.

## The server ending itself about a second after start
- Twice (10:09 and 11:43 on 6 Nov, builds with no relation to each other) the process was ended by `TerminateProcess(3)` (exit code 3 is what `abort()` gives) from the game's own code, about 1.0 to 1.1 seconds after "Finished initialization!" and before any player joined. The stack shows only the thread's start routine and the game function that ends the process, so it is a thread of the game that is not the game thread, not our code. Most starts do not die.
- The exit log now lists, after the stack, the thread that ended the process (when it was created, where it runs, which functions created it) and the last twelve threads created, plus the modules loaded since startup (`Modules (at startup)` lists them once). `NtCreateThreadEx` is hooked right after MinHook starts to keep that record.

## The hub that does not load (6 Nov, 11:53 run)
- In a run that could not be joined the server asked for the three hub levels at 11:53:49 and the world still had 0 streaming levels a minute later; the three streaming foundations existed (enabled state 1, level to stream set) and the requests at 10 s and 30 s changed nothing. The same code loaded the hub in 1 s in other runs, so the game's own way of streaming them fails now and then.
- After 15 s of waiting the end of the engine's own log (`Saved/Logs/FortniteGame.log`) is copied into `xenbono.log` (lines about levels, streaming, errors, failures; prefix `LogEngine`), and again when the process ends. After 20 s a level that still has no streaming level is loaded directly with `ULevelStreamingDynamic::LoadLevelInstance`, named like the level itself.
- 6 Nov, 12:03 run: the hub was loaded directly after 20 s, the server listened, the island was set up and its level streamed on the server (`OnFinishedLoading`, floor tiles registered), but the player spawned in the air with no island: the client never got the levels either (its hub and island come from the same streaming that failed on the server). Changes: the direct load now comes after 8 s, the extra foundations at 10 s and 30 s are no longer made, the presetup waits (at most 30 s) while the asset registry is still loading assets (a request made during that can be lost; the state is logged at the presetup and in every hub report), the playlist-levels-have-streamed-in events of the game are called after a direct load, and the island setup now writes every streaming level with its state and the island stream component's contents.
- 6 Nov, 12:13 run (every run since the 11:40 build needed the direct load): the server had all levels and the island streamed fine, the client still had no map. A streaming foundation has a replicated flag `bServerStreamedInLevel` (set by the foundation's own streaming when the server has streamed its level in) that the clients wait for before they load the level. When the levels are loaded by hand the foundations never set it, so after a direct load the flag is now set on every streaming foundation (`OnRep_ServerStreamedInLevel`, net update). The foundation report in the log also shows the foundation's own streaming level (`LevelStreamInfo`) and that flag. The world's `StreamingLevels` list is not where a foundation keeps its level, so "0 streaming levels" in the hub report does not by itself mean the foundation has none.
- 6 Nov, 12:29 run: the exit log traced the process end to a thread that was created before the thread hook was installed (so by the game's startup, not by this DLL): it runs a start routine in the exe (0x56E4D7E) that calls the exe's exit function (0x67269E) directly, which calls `TerminateProcess(3)`. The threads created shortly before are the NVIDIA driver's (the GS window's DirectX device). It is the same call as in the 10:09 and 11:43 crashes. What the thread is for is not known. Workaround: `TerminateProcessHook` parks a thread of the exe that calls `TerminateProcess` with exit code 3 (it sleeps forever inside the hook) instead of letting it end the process; the tick box "Keep the server running if the game tries to end itself (exit code 3)" in the GS window (`Globals::bKeepServerAlive`, on by default) turns it off. Every exit is still written to the log.
- 6 Nov, 12:39 run: parking the thread that calls `TerminateProcess(3)` froze the game (no log line after it, no "Waiting for the hub" reports): the thread is the MAIN thread. Its start routine (exe + 0x56E4D7E) is the exe's entry point and the function it calls (exe + 0x67269E) is the exit of the C runtime, so WinMain returned 3: the engine left its main loop because something asked it to exit with status 3. The parking was removed again. The engine log is not in the game folder but in `%LOCALAPPDATA%\FortniteGame\Saved\Logs\FortniteGame.log`; the exit log now reads that file (the newer of the two candidates) and writes its last 40 lines, which should hold the reason for the exit request.
- 6 Nov, 12:56 run (no exit this time): the hub was loaded by hand after 8 s, the three foundations were marked, a player joined and the island was set up and streamed on the server, but the client still had no map. The foundation report shows `server streamed in 1` from the very first report, so that flag was never the problem, and `own streaming level none` for all three: the foundations' own streaming (their `LevelStreamInfo`) never starts, on the server and so very likely on the client. Added to find out why: a full property dump of one foundation (`Streaming foundation dump`), the end of the engine log at the moment the direct load is needed, one more `OnRep_LevelToStream` / `OnRep_DynamicFoundationRepData` on every foundation after 3 s, and levels that a foundation streams itself (its `LevelStreamInfo`) are not loaded a second time.

## The server ending itself (SOLVED, 6 Nov 13:05 log)
- The engine log copied into `xenbono.log` at the exit named it: `LogWindows: Error: Unhandled Exception: 0xe06d7363` (a C++ exception) thrown from `XENBONO.dll!std::_Throw_Cpp_error` inside `LogCreativeProcessEvent` (die.h), called from `ProcessEventHook` via `UObject::GetFullName` and `UKismetSystemLibrary::GetPathName`. `GetFullName` is itself a ProcessEvent call, so while the hook held the logging lock it re-entered the hook and took the same non-recursive lock again on the same thread, which throws; the exception reached the game's crash handler, which asks the engine to exit (`RequestExit`), the main thread returns from WinMain with status 3 and the C runtime calls `TerminateProcess(3)`. That is every "TerminateProcess(3) about one second after the start" of 6 Nov (and likely earlier ones). Not the game's protection, not the backend, not the launcher.
- Fix: the hook now runs all its own work with a per-thread flag set (`bInProcessEventHook`); a ProcessEvent made by our own code meanwhile goes straight to the game without logging. The parking workaround and its tick box were wrong (the parked thread was the main thread) and are gone.

## What the 6 Nov 15:20 run showed, and the new prefab layout
- The hub works again (the island appears), the devices spawn, the crash is gone. The prefabs were still wrong, and the log said why: the barn (`PID_019_PG_Farmstead_M_Barn_a`) lists 34 piece classes but the builder only took the 24 with the biggest counts, so the rarest and biggest pieces (doors, roof peaks, the steeple) were never built; the walls were dealt round the outside one after the other (arches, walls and windows mixed), and the roofs were tiled flat on a grid. `GameplayProps` is 17 coins and `DestroyTarget` is 10 destructible targets: not buildings, but they got a wood house.
- The real prefabs can be seen in the client's own prefab menu (the thumbnails): the barn is a red wooden barn with a gambrel roof, a lean-to on one side, a cupola on the ridge, a big open door at the front and hay bales in front. The recordings of the menu (`Fortnite_16a12364...mp4`, 11 s and 13 s) are the only source of what the real ones looked like, the client has no layout data.
- New layout, `XENBONO/PrefabArchitect.h` (no game types in it, so it can be run and drawn on its own, see `XENBONO/tools/PrefabPreview`): it gets the pieces as types (kind from the class name, count, box, shape of the top) and returns where each goes.
  - A playset with walls, roofs or floors becomes a building: the pitch is the width of the wall panels, the height of a level the shortest main panel; the core is the largest rectangle that fits the volume (a yard round it when there are props) and the fewest levels that leave at most 40 percent of the panels over; the door is centred in the front (a door wider than its face is cut to it), arches are spread over the ground level (at most 40 percent of it) and in the middle of the front and back above, windows on the second level, plain walls one kind per face and level; arches and walls that are left become inside arcades and walls; corner posts; a hay loft round the walls on the first level (the middle open, rails along its edge) or a ground floor; stairs along the west wall; a roof; features (steeple, cupola) on the ridge; props in tidy rows in the yard (front on both sides of the door, east, west, back, inside, then outer rings), small ones stacked up to three high; no prop is left out, roofs/walls/floors that are not needed are.
  - A playset with only props, and every `..._Gallery_...`, becomes an exhibit: one row per kind of piece.
  - Roofs: tents (gable tiles) are laid on every slot with the ridge along the long side, stretched along the ridge when there are too few; sheds (one slope) are paired along the ridge and stretched (scale, keeping the pitch) so one or two of them span from the eave to the ridge without a gap; the end caps close both ends. The shape of every roof piece, cap and stairs comes from a 7 x 7 grid of rays dropped on the spawned piece (`ProfileShape`, `KismetSystemLibrary::LineTraceSingle`): flat, one side high (which), or high in the middle (which way the ridge runs).
- Measuring: each class is spawned once high above the prefab, its box and shape read, and removed again; remembered for the next throw. Classes are no longer capped (volumes, controllers, pawns and game modes are skipped).
- Devices: a device whose playset name differs from its map or folder name is found anyway (`CreativeButton` is `CP_Devices_Button`; names are compared without underscores and without a leading "creative"); `PID_019_PC_Device_<Name>` (the radio) is handled like `PID_CP_Devices_<Name>`; the maps of devices in other folders (`/Game/Creative/Radio/CP_Device_Radio`) are listed; device actors are made to replicate (an actor that does not is never seen by a client).
- Logging: for every prefab built the log has `Architect input:` lines (the size and every piece type with kind, count, box and shape), `layout:` notes and the box check. `XENBONO/tools/PrefabPreview/extract.py` turns them into description files; `preview.cpp` runs the layout on one, `render.py` draws it from four sides. The "Write every prefab's pieces to the log" button (`Globals::bSurveyPrefabsRequested`) does the same for every playset in `/Game/Playsets`, one every quarter second.
- The layout was fuzz-tested (20,000 random prefabs, no crash, no hang, no position out of range, no piece placed more often than listed, 5 ms at most) with a checked standard library.

## Device options and island settings (6 Nov, from the 12.41 SDK dump)
- Public sources say nothing about how these work inside the game (Epic only documents what each device's options do). The real layout is in the Dumper-7 SDK of 12.41 (`SDK.rar`, in the Downloads folder, not in the repo): look in `FortniteGame_classes.hpp` for `UFortActorOptionsComponent` and `AFortPlayerController`.
- A device's options and the island's settings are the same system. The actor has a `FortActorOptionsComponent` (`PlayerOptions`: the asset that lists its options; `PlayerOptionData`: the changed options as replicated overrides; `SetPropertyOverrides` / `SetPropertyOverrideValues` / `GetPropertyOverrides` with a `TMap<FString, FString>`; `CanEditOptionsComponent(pawn)`, which the client asks before it opens the options screen). The island's settings machine (`MinigameSettingsMachine_C`, an `AFortMinigameSettingsBuilding`) has a `ToyOptionsComponent_C`, which is a subclass of it (`IsMachine`), and its replicated game settings (time limit, number of teams, lives, rounds ...).
- The client changes options with requests on the player controller: `ServerUpdateActorOptions(actor, keys, values)` for a device, `ServerUpdateGameplayOptions(keys, values)` for the island's game settings, `ServerUpdateMessageComponents` (billboard, HUD message), `ServerUpdateItemListOptions`, `ServerUpdateGameDescriptionData`, `ServerBroadcastDeviceButtonComponentClickedDelegate` (a button in a device's options screen); interacting with a device is `FortControllerComponent_Interaction.ServerAttemptInteract`. The handlers are the game's own native code.
- Why the logs never showed any of it: the creative ProcessEvent log filter (`die.h`) threw away every function with "ServerUpdate" in its name (to hide the movement spam), so these requests were called and not written down. They are logged in full now.
- `CreativeSettings` (FortAthenaCreativePortal.cpp): every one of these requests is written to the log (what was asked, the options before, what the game's handler left set, and whether the player may edit: the game's own `CanEditOptionsComponent` answer for the pawn). When the game's handler did not set the requested options, they are set through the component's own functions, with a `TMap<FString, FString>` built by hand (one hash bucket, entries 0x28 bytes, the key at +0 and the value at +0x10) and checked again afterwards. The island's game options are checked against and, if missing, set on the settings machine's options component.
- Devices: every device placed by our own code is checked and written to the log (`Device check:`): its options component, the options asset, what is set, whether the player may edit it, and once for each kind of device every property of the actor (`Device dump`). `AFortMinigame` (the island's minigame object, `Minigame_PlayerCreated_C`) owns the teleporter manager component and the creature manager, devices register with it through the volume manager when they overlap the island volume.
- The button "Test: place every device in a grid next to the first player" places every device playset (`PID_CP_Devices_*`, `PID_019_PC_Device_*`) next to the first player, 8 to a row, so every device can be tried in one go and the log has the check of each.

## The hub map missing on the client again (6 Nov, 16:38 run) and the real way the playlist levels reach clients
- The 16:38 run: the same as the runs before. The game's own streaming of the three hub levels never started on the server (`own streaming level none`, 0 streaming levels at 0, 4 and 8 s), the direct load at 8 s gave the server its hub (`FortPlayerStartCreative` actors, island set up when the player joined 1.5 s later), the client joined and had no map. The log ends 37 s after the start (27 s after the join). There is no client log of that run; the engine log copy at the failure holds nothing about levels.
- What was found in the 12.41 SDK: `AFortGameState::AdditionalPlaylistLevelsStreamed` (`TArray<FAdditionalLevelStreamed>`, 12 bytes each: `FName LevelName`, `bool bIsServerOnly`) is `Net` and `RepNotify`; its OnRep (`OnRep_AdditionalPlaylistLevelsStreamed`) streams the levels it lists, on a client from the replicated list and, called by hand, on the server. That is the game's own way of getting the playlist levels to the clients. The project did not use it: `AddToAdditionalPlaylistLevelsStreamed` was `if (true) StreamLevel(...)`, a `BuildingFoundation3x3` per level ("skunke bozo"), whose streaming on the server starts or not from run to run, and the clients' load depends on that foundation's replicated flags reaching them at the right moment. After a direct load on the server (a fallback for the server only) nothing at all tells a client to load.
- Change: in Creative the level is put into the game state's replicated list (no duplicates, the 12 byte struct zeroed), the OnRep that the presetup already calls streams the levels on the server, and every client streams them from the same list by itself, whatever the server's own streaming does. Other modes keep the foundation. The log says at the presetup how many entries the list has and how many streaming levels the world has right after the OnRep; the 8 s direct load stays as the fallback for the server only.
- If the client still has no map with this, the file that settles it is the client's own `FortniteGame.log` (`%LOCALAPPDATA%\FortniteGame\Saved\Logs`) of that run: `LogStreaming`, `LogNet`, `LogFortWorld` and `LogLevel` lines after the join say whether the client asked for the levels and what failed.

## The crash 0.2 s after a player joined (6 Nov, 16:57 run), caused by the faster hub
- The new playlist-level list worked on the server: the OnRep streamed all three levels at once (`the world has 3 streaming levels` at 0 s) and the player starts existed after 1 s. The player joined at 16:57:45, and at 45.262 the log has `LogCrash: Exception 0xC0000005 at 0x0` (a call through a null pointer) on another thread, in the middle of the startup's hook installation (`Hooking 0x42c3ed0` is the line before it; "Finished initialization!" was never reached, the startup was still hooking at 46.1 s).
- Two causes. (1) `Hooking::MinHook::Hook` called `MH_EnableHook` first and set the caller's pointer to the original function afterwards: a thread that called the function in the moment it was patched ran the detour with a null `Original` and jumped to address 0. The pointer is now set before the hook is enabled. (2) The DLL's startup thread takes about 18 s to install all its hooks and runs while the game is already running; until now the hub took 8 s or more to load, so the startup was nearly always finished before anybody joined. With the hub loading in a second a player joined in the middle of it. In Creative `Athena_ReadyToStartMatchHook` now returns false (the game is not ready, so nobody can join) until the startup sets `Globals::bInitializationFinished`, at most 90 s, and says so every 4 s in the log.

## Devices inert after the 18:5x build: a dangling pointer in `CreateSpawnParameters` (6 Nov, 19:49 log)
- In that log every device spawned on the server (`Own device X: 2 actors spawned`) but none of their Blueprints ever ran: not one `ProcessEvent` of any device class (the 13:20 run had the vending machine's `CycleToNextItem` and others), the speaker's `Mesh`/`Audio` component variables were null right after the spawn and no device had an options component. A Blueprint actor whose construction was deferred looks exactly like that (no Blueprint components, no construction script, no BeginPlay): invisible and doing nothing.
- Cause: `CreateSpawnParameters()` (World.h) returned a pointer to a local variable (`FActorSpawnParameters addr{}; return &addr;`). The caller passes it to the engine's SpawnActor after the function has returned, and the engine's own frame sits where that local was, so the flags it read (among them `bDeferConstruction`) were stack leftovers. When the compiler inlines the function the local lives in the caller's frame and it works; the big creative source file got large enough to stop that inlining, which is why devices (spawned with `SpawnActor<AActor>`) broke after the last commits while building pieces did not. It also explains "some devices spawn" before: it depended on the call site.
- Fix: the parameters sit in a ring of 64 thread-local slots (`NextSpawnParametersSlot`), zeroed for every use; the second `SpawnActor` overload no longer calls `VirtualFree` on them. Every actor spawned through `UWorld::SpawnActor` in any mode gets proper parameters now.
- Radio and Button maps: `RegistryAssets` returned nothing when the device maps were listed (the same weak spot as before), so the loose name matching had no candidates. The 47 device maps the survey listed are now a fixed table (`KnownDeviceMaps`) merged into the list, so `CreativeButton` finds `CP_Devices_Button` and `Radio` finds `/Game/Creative/Devices/Radio/CP_Device_Radio`.

## Device options that do not apply, the phone's HUD, prefabs with holes (6 Nov, after the 20:33 run)
- Options. In the 20:33 log the Billboard's options screen sent `ServerUpdateActorOptions` with six options (`UserDefinedText=celestrix, TextSize=Small, HorizontalTextAlignment=Left, TextFont=Roboto, TextColor=White, BackgroundColor=Black`). The game's own handler left 0 of the 6 set, and both `SetPropertyOverrideValues` and `SetPropertyOverrides` of the device's `ToyOptionsComponent_C` returned false. The values are the names the screen shows, not the values the actor holds (`TextSize` is an int, `TextColor` a `LinearColor`, `UserDefinedText` is not even replicated), and the options asset (`Creative_Billboard_UserOptions`, a `PlaylistUserOptions`) is what maps one to the other (enum options list `DisplayName` and `OptionValueName` for every value, int, float and color enums also the value).
- The component's `PlayerOptionData` (`FPropertyOverrideData`) has a `BaseObject` that the overrides apply to. Whether the game leaves it empty on a device that was spawned by this server is not known yet (the log never showed it), so the code writes it down. After the game's handler, when options are still missing the code now: (1) writes the component, its `PlayerOptionData` (override count, mode, base object, mutable object), the options asset (every option with its class, key and values) and, once for each kind of component, all of the component's properties (`Options component ...`, `Options asset ...` lines); (2) gives the data its base object (the actor) when it has none and runs the component's setters again; (3) runs `ResolvePendingRepOverrides`; (4) when that still leaves options missing, looks each option up in the asset, turns its value name into the real value, writes it into the actor's property of the option's name (int, byte or enum, bool, float, string, `LinearColor`), runs the property's `OnRep_` function, and adds an entry to the component's override list (the replicated list the clients apply). Each step is one `Settings:` line, including every option the code could not set and why.
- Not verified: whether the native setters work once the base object is set, whether the hand-written override entries are what the client's `OnRep_PlayerOptionData` expects, and the "[Parameter name] / Option" row of the screen (it is built on the client from the asset and its localization, which the server does not touch). The log will say which of the steps did the work.
- The phone's HUD. The SDK shows the controller has two replicated flags the client's creative HUD depends on, `bIsCreativeModeEnabled` and `bIsCreativeQuickbarEnabled` (repnotify), and a replicated `CreativeQuickbarComponent` the game makes from the soft class `CreativeQuickbarClass`. Nothing in this project set or even read any of them, so the phone could be in the inventory and the client still had no creative HUD. `CheckCreativeHud` (called when the phone is given and on each of the four retries) writes the three flags (`bIsCreativeQuickmenuEnabled` as well) and the component to the log, sets the flags that are off (and runs the `OnRep_` functions), runs `GrantCreativePhoneItemDefLoadedCallback` when the component is missing, and if it is still missing loads `CreativeQuickbarClass`, makes the component with `SpawnObject` (outer: the controller), replicates it and runs `OnRep_CreativeQuickbarComponent`. Lines: `Creative HUD (...)`.
- Prefabs with holes. The 20:33 log shows the structural check at work: five `Farm_Roof1_S` pieces of the barn got `BlueprintOnStructurallyUnstable` and were removed (`RemoveActorWhenDied`) within a second of the barn being built. `SpawnPiece` marks every set piece with `ABuildingSMActor::bForciblyStructurallySupported` (offset 0x6A3, bit 7), which the game's `IsStructurallySupported` reads, so scenery that no grid cell holds up is not collapsed. The layout itself (rendered offline from the same log) has no holes: 193 of 193 pieces for the barn, with the roof closed.
